# RN 转 H5

将 RN 代码迁移成可维护的 H5 React/TypeScript 实现。目标是保留业务行为和页面结构，优先复用当前库已有能力，而不是逐标签机械翻译。

以用户给出的 RN 源页面和 H5 目标为准。读取 RN 源码只用于理解待迁移行为；组件和工具的 H5 API 仍以当前项目 `.ai/docs/` 为唯一知识库。

## 支持边界

- 优先迁移使用与当前库同类组件、组合和 utils 的页面。源码里出现的控件名、工具名，对照 `.ai/docs` 自行判断是否已有对应能力，不要假定必须来自某个固定 RN 包名。
- 可以有限转换 `react-native` 基础布局、文本、图片、交互和样式，但要服从目标项目已有结构与规范。
- 不保证自动转换任意第三方 RN 库、原生模块、导航栈、动画、手势、地图、相机或文件系统能力。
- 同名组件或 util 只代表高优先级候选，不代表 Props、Ref、事件、返回值或行为兼容。
- 不得通过安装 `react-native-web` 来掩盖迁移缺口，除非用户明确选择该技术路线。

## 问答入口

启动技能后，先检查用户当前消息是否已经提供以下两个地址。地址是本地文件或目录路径，不是浏览器 URL：

1. **RN 源页面地址**：待转换页面的入口文件或页面目录。
2. **H5 目标页面地址**：生成结果要写入的现有页面文件、现有页面目录或新页面目录。

缺少任一项时，在同一轮简洁询问缺少的信息。两项都缺少时使用以下问法：

> 请把 RN 源页面地址和 H5 目标页面地址发给我，例如：
>
> - RN：`/path/to/rn-project/src/pages/OrderDetail`
> - H5：`/path/to/h5-project/src/pages/OrderDetail`

用户已经提供的信息不要重复询问。收到路径后先做只读检查：解析相对路径、确认 RN 入口、判断 H5 地址是现有文件/目录还是待创建路径，并检查目标项目结构。路径不存在或指向不明确时，说明具体问题并只追问该路径。

若 H5 目标中已有实现，先判断能否安全地按现有结构迁移。只有覆盖、合并或保留现有实现会实质改变结果且用户意图不明确时，才追加询问；不得未经确认覆盖重要现有代码。

两个地址明确后，默认直接完成分析、生成和验证，不再要求用户确认常规的组件映射或实现细节。仅当原生能力没有可靠 H5 等价物、需要新增依赖或需要改变目标项目架构时，才暂停并提出最少量的必要问题。

## 转换流程

### 1. 确认迁移范围

读取 RN 入口及其直接依赖，确认目标目录、目标路由和预期交互。若用户只给页面名或相对路径，先在其给出的 RN 工程中定位。默认只写入 H5 目标，不要改 RN 源码。

只迁移请求范围内的文件。先查看目标项目已有页面、路由、请求层、状态管理、样式方案和国际化约定，避免另建一套结构。

### 2. 建立依赖清单

从入口递归到本次迁移所需的本地依赖，按用途分类整理：

1. UI 组件与类型。
2. 工具函数。
3. `react-native` 基础组件、API 与 StyleSheet。
4. 第三方 RN 包和原生模块。
5. 路由、网络请求、存储、设备能力及桥接调用。
6. 图片、字体、图标和其他静态资源。

先记录用途和行为，再选择 H5 替代项；不要只按 import 名称批量替换。

### 3. 优先匹配 H5 docs

对依赖清单中的每个业务组件和 util，使用现有 docs 解析器检索：

```bash
node .ai/skills/develop/scripts/resolve-docs.mjs --query "组件名,工具名,业务场景"
```

按命中结果读取对应 `*-props.ts` 和 `*-rules.md`；只有需要具体组合写法时再读取 `*-example.md` 及其指向的 demo。通常每项保留最相关的 1 ～ 5 个候选。

匹配时按以下优先级决策：

1. H5 docs 中同名且语义一致的组件或 util。
2. H5 docs 中名称不同但业务能力一致的组件或 util。
3. 目标项目已有的 Web 实现。
4. 小范围使用语义化 HTML、CSS 和浏览器 API 实现。
5. 无可靠替代时标记迁移缺口并说明影响。

即使 RN 与 H5 两端名称相同，也必须根据 H5 `props` 和 `rules` 重写调用。禁止沿用 docs 中不存在的 Props、子组件、枚举、Ref 或方法。

### 4. 转换平台能力

- 将 `View`、`Text`、`Image`、`Pressable`、`ScrollView` 等基础组件按语义转换；当前库组件能表达相同行为时优先使用库组件。
- 将 RN style 对象改为目标项目现有的 Web 样式方案。不要直接保留 `StyleSheet.create`、数字尺寸语义、RN 阴影或仅 RN 支持的样式属性。
- 重新核对事件模型，例如 `onPress`、文本输入、滚动、键盘和返回键；不要假定与 DOM 事件等价。
- 路由、存储、剪贴板、定位、媒体、扫码等能力先查 H5 utils/component docs。只有目标运行环境明确提供 `lyrixi` JS Bridge 时，才可按其实际类型或文档接入；否则使用已确认的浏览器/项目能力或列出缺口。
- 第三方 RN 包逐个判断 Web 替代方案。新增依赖、改变路由架构或引入兼容层前先向用户说明。

### 5. 实施与验证

实现必须使用 `.ts`/`.tsx`，遵守目标项目的规则与目录结构。业务代码从 `lyrixi-web` barrel 导入；不得留下 RN 组件库或 `react-native` 的运行时依赖。

完成后至少检查：

- 搜索迁移范围内残留的 RN 组件库、`react-native` 和 RN 专属包导入。
- 对照 docs 复核所有新增的库组件 Props、子组件和 utils 调用。
- 运行目标项目已有的格式化、TypeScript、ESLint、测试或构建命令中与改动相关的部分。
- 核对加载、空态、错误、提交、返回、滚动、弹窗及资源路径等关键状态。

## 交付说明

简要列出已转换范围、采用的主要 H5 组件/utils、验证结果，以及仍需原生能力、产品决策或人工联调的缺口。部分能力无法可靠迁移时保留明确的待办标记或迁移报告，不要静默删掉业务行为。
